# 이상탐지 / 위험 스코어링 시스템 — 16시간 멘토링 기획서

CERT r4.2 인사이더 위협 데이터셋 기반 · z-score 통계 이상탐지 · 멀티 로그 타입

---

## 1. 프로젝트 개요

### 한 줄 정의
보안 로그를 분석해서 사용자별 "위험 점수"를 자동으로 계산하고, 위험한 순서대로 순위를 매기되, 각 사용자가 왜 위험한지 근거까지 제시하는 시스템을 만든다.

### 목표
- "정상 행동"의 기준을 데이터로 정의하고, 거기서 벗어난 정도를 점수화하는 통계 기반 이상탐지를 직접 구현한다.
- 머신러닝 없이 baseline + z-score만으로, 설명 가능한 스코어링 시스템을 완성한다.
- 데이터에 이미 심어져 있는 인사이더(정답)를 우리 시스템이 상위로 잡아내는지 정량적으로 검증한다.

### 최종 산출물
- 사용자별 위험도 순위표
- 각 순위 항목에 대한 근거 문장 (예: "새벽 2시 로그인 4회, 평소 0회 / USB로 파일 12개 복사, 평소 0개")
- "심어둔 인사이더 N명 중 M명을 상위 10위 안에 탐지"라는 검증 결과
- 조회용 리포트 또는 간단한 화면 + 발표자료

### 대상·형식
- 16시간 집중 멘토링 (개념 스터디 블록 없이 바로 프로젝트 진행)
- 팀 단위 진행
- z-score 등 핵심 개념은 필요한 순간에 15분 내외로 인라인 설명

## 2. 무엇을 만드나 (최종 결과물 상세)

학생 팀이 만드는 것은 "사용자별 위험 점수를 자동으로 계산해서 순위를 매기는 시스템"이다.

- 입력: 보안 로그 (로그인, 기기, 파일, 웹, 이메일 이벤트)
- 처리: 사용자별 "평소 행동" 기준선(baseline)을 데이터로 계산 → 벗어난 정도를 점수화
- 출력: 위험도 순위표 + 각 항목의 "왜 위험한지" 근거 + 검증 결과

예시 결과 화면:

```
순위  사용자      위험점수   주요 근거
1     MYD0930     91        새벽 로그인 4회(평소 0), USB 파일복사 12건(평소 0), 유출사이트 접속
2     LRR0148     74        평소 안 쓰던 PC 5대 접근, 외부메일 대용량 첨부 3건
3     BTQ1846     63        파일 접근량 평소 대비 18배
```

## 3. 핵심 원리

이상탐지의 뼈대는 하나다: **"이 사용자가 평소랑 얼마나 다른가?"**

1. **베이스라인 만들기** — 각 사용자의 "평소 모습"을 통계로 정의한다 (평소 로그인 시간대, 평소 접근 PC 수, 평소 파일 접근량 등의 평균·표준편차).
2. **이탈도 측정 (z-score)** — 오늘 행동이 평소에서 몇 배 벗어났는지 측정한다. z-score = (오늘값 − 평소평균) / 평소표준편차.
3. **여러 신호 합산** — 여러 이탈 신호를 가중치로 합쳐 하나의 위험 점수로 만든다.
4. **근거 붙이기** — 점수만 주지 않고, "왜 위험한지"를 근거 문장으로 자동 생성한다. 실무 가치의 핵심이다.

머신러닝은 쓰지 않는다. 통계 기반(rule + z-score)으로 충분하고, 설명 가능해서 초심자·발표에 유리하다.

## 5. Feature 설계

z-score는 "사용자별 · 하루 단위 숫자"에 매긴다. 따라서 모든 feature는 "이 사용자가 오늘 하루 OO을 몇 번 했나" 형태의 일별 집계값이다.

| 로그 타입 | Feature (사용자별·일별) | 이 값이 크면 = 무엇을 잡나 |
|---|---|---|
| logon | 비근무시간(밤·새벽) 로그인 횟수 | 평소 낮에만 일하던 사람의 새벽 활동 |
| logon | 로그인한 서로 다른 PC 수 | 남의 자리·여러 대 이동 (측면이동) |
| logon | 일별 로그인 횟수 | 평소 패턴 이탈 |
| device | 비근무시간 USB 연결 횟수 | 몰래 자료 반출 정황 |
| device | USB 연결한 PC 수 | 평소 안 쓰던 USB 사용 |
| file+device | USB 연결 시간대의 파일 접근 수 | USB 사용 중 대량 파일 접근 정황 |
| file | 일별 파일 접근 수 / 서로 다른 파일 수 | 평소보다 대량으로 파일 수집 |
| http | 방문한 서로 다른 도메인 수 | 평소 안 가던 사이트 활동 급증 |
| http | 유출·구직·업로드 사이트 방문 | 이직 준비·자료 유출 정황 |
| email | 외부 도메인으로 보낸 메일 수 | 자료를 외부로 발송 |
| email | 첨부가 있는 외부 메일의 `size` 합계 | 대용량 자료 외부 반출 정황 |

> r4.2의 `file.csv`에는 USB 복사를 직접 나타내는 `to_removable_media` 컬럼이 없다. 따라서 device의 Connect–Disconnect 구간과 동일 사용자·PC의 file 이벤트를 시간 기준으로 결합해 **USB 연결 중 파일 접근**이라는 대리 지표(proxy)를 만든다. 이는 실제 복사를 확정하는 값이 아니므로 결과 문장도 "복사"가 아닌 "USB 연결 중 파일 접근"으로 표현한다.

> email의 `attachments`는 첨부 개수이고 `size`는 메일 크기다. 첨부 파일 자체의 총용량으로 해석하지 않는다.

### Feature 도입 순서 (중요)
1. **1단계 (필수):** logon 3개 (비근무시간 로그인·PC 수·로그인 횟수)로 전체 파이프라인을 한 바퀴 완주.
2. **2단계:** file(대량 접근), device(비근무시간 USB), USB 연결 구간과 file 이벤트의 시간 결합 추가.
3. **3단계 (여유 시):** http(도메인 수·유출사이트), email(외부발송·첨부 메일의 `size`) 추가.

처음부터 5개 타입을 동시에 열면 학생들이 흔들린다. logon으로 뼈대를 세운 뒤 확장한다.

## 6. 정규화 (전처리의 핵심)

### 문제
로그 타입마다 컬럼이 다르다. 앞부분(id, date, user, pc)은 공통이지만 뒷부분이 제각각이다.

| 파일 | 공통 앞부분 | 제각각인 뒷부분 |
|---|---|---|
| logon | id, date, user, pc | activity (Logon/Logoff) |
| device | id, date, user, pc | activity (Connect/Disconnect) |
| file | id, date, user, pc | filename, content |
| http_sampled | id, date, user, pc | url, content |
| email_sampled | id, date, user, pc | to, cc, bcc, from, size, attachments, content |

그냥 위아래로 붙이면 컬럼이 안 맞아 뒤죽박죽이 된다. 그래서 하나의 공통 스키마로 통일해야 한다.

### 목표 공통 스키마
```
event_time, event_date, user, pc, event_type, action, detail, value, flag, source
```

### 정규화가 하는 3가지
1. **컬럼 통일** — 제각각인 뒷부분을 공통 컬럼(event_type, action, detail)으로 흡수.
2. **값 형식 통일** — 날짜 문자열("01/05/2010 02:14:09")을 진짜 datetime 타입으로 변환. 이게 돼야 시간대·일별 집계가 가능.
3. **의미 정렬** — 서로 다른 파일의 값을 같은 뜻이면 같은 자리로. content 등 안 쓰는 컬럼은 버리고, http는 도메인만 추출.

### 타입별 매핑 예시
- logon: activity → action (event_type=logon)
- device: activity → action (event_type=device)
- file: filename → detail (event_type=file), content 버림
- http: url에서 도메인만 추출해 detail (event_type=http), content 버림
- email: 수신자 도메인으로 외부 발송 여부 → flag, `size` → value, `attachments`는 첨부 개수로 보존, content 버림

정규화 결과는 메모리와 I/O 부담을 줄이기 위해 로그 타입별 파일로 먼저 저장한다. 최종 병합 지점은 모든 원시 이벤트가 아니라 훨씬 작은 `daily_features.csv`로 삼는다.

```text
Data/Data for Class/
└── normalized/
    ├── logon_normalized.csv
    ├── device_normalized.csv
    ├── file_normalized.csv
    ├── http_normalized.csv
    └── email_normalized.csv
```

사용자 타임라인이 필요한 USB 구간 결합 등에만 정규화 이벤트를 user+시간 순으로 사용한다. 여유가 있다면 CSV 대신 Parquet으로 저장해 용량과 로딩 시간을 줄인다.

## 7. z-score 계산

### 방법
사용자별로 각 feature의 일별 값을 집계한 뒤, **평가일 이전 데이터만으로** 평균(mean)·표준편차(std)를 계산해 baseline을 만든다. 평가 대상 날짜를 baseline에 포함하면 이상 행동이 평균을 끌어올리는 미래 데이터 누수와 점수 희석이 발생한다.

```
baseline_mean(t) = mean(x before t)
baseline_std(t)  = std(x before t)
z(t) = (x(t) - baseline_mean(t)) / baseline_std(t)
```

구현은 초기 학습 기간을 고정하거나 `shift(1) + rolling(window)`을 사용한다. 최소 관측일 수가 부족한 사용자는 전체 또는 LDAP 동료 집단 baseline으로 보완한다.

예: 평소 비근무시간 로그인이 하루 0.3회(std 0.5)인 사용자가 오늘 8회 로그인
→ z = (8 − 0.3) / 0.5 = 15.4 → 평소 변동 범위에서 크게 벗어남.

### 반드시 만나는 함정: std = 0
"비근무시간 USB 연결" 같은 feature는 대부분 사용자의 평소 값이 0이라 표준편차가 0이다. 그러면 0으로 나누기가 발생해 z가 무한대가 된다.
- `std = 0`이고 오늘 값도 평균과 같으면 `z = 0`.
- `std = 0`인데 오늘 값이 평균보다 크면 별도 rule score를 부여.
- 일반 z-score는 `0 ≤ z ≤ 10`처럼 양의 방향만 사용하고 상한을 두어 한 신호가 전체 점수를 독점하지 않게 한다.
- epsilon만 더하면 작은 차이가 지나치게 큰 점수로 증폭될 수 있으므로 보조 수단으로만 사용한다.
- 이건 버그가 아니라 교육 포인트다. 학생들이 직접 부딪히고 해결하게 한다.

## 8. 스코어링 로직

여러 feature의 z-score를 가중치로 합쳐 하나의 위험 점수로 만든다.

```
daily_risk = w1·clip(z(비근무로그인)) + w2·clip(z(USB연결중파일접근)) + ...
user_risk = 사용자의 일별 점수 중 최댓값 또는 상위 N일 평균
```

- 가중치는 정답이 없다. "왜 이 가중치인지 논리를 대라"고 요구하는 것이 교육의 핵심.
- 유출과 연관된 신호(USB 연결 중 대량 파일 접근, 첨부가 있는 외부 대용량 메일)에 높은 가중치를 주는 식의 근거 있는 설계를 유도한다.
- 사용자별 단순 누적합은 재직 기간과 활동일이 긴 사용자에게 유리하므로 사용하지 않는다.
- 최종적으로 점수 내림차순 정렬 → 위험도 순위표 v1 산출.

## 9. 검증 방법

이상탐지의 가장 큰 함정은 "우리 시스템이 잘 잡는지 확인할 방법이 없다"는 것이다. CERT는 answers 폴더에 정답(누가 인사이더고 언제 무슨 짓을 했는지)이 들어 있어 이 문제를 해결한다.

### 검증 흐름
1. answers를 **보지 않고** logon/device/file(+http/email)로 스코어링 시스템을 만든다.
2. 위험 점수 순위표를 산출한다.
3. **이제 answers를 열어** 실제 인사이더 명단과 대조한다.
4. "인사이더 70명 중 M명을 상위 K위 안에 잡았나?"로 성능을 평가한다.

### 핵심 평가 지표
- `Recall@10`, `Recall@20`, `Recall@50`: 상위 K명 안에서 찾은 인사이더 비율
- `Precision@K`: 상위 K명 중 실제 인사이더 비율
- 실제 악성 활동 기간에 높은 일별 점수가 발생했는지 확인하는 기간 적중률
- 순위에 오른 사용자별 근거 문장의 원본 로그 대조

answers를 보고 가중치를 바꾸면 같은 정답으로 학습과 평가를 동시에 하는 셈이다. 따라서 **정답 공개 전 baseline 결과**와 **튜닝 후 결과**를 분리해 보고한다. 가능하면 시나리오 또는 기간을 튜닝용·최종평가용으로 나눈다.

answers는 분석 재료가 아니라 시험지 채점용 해답지다. 분석 중에 미리 보면 의미가 없어진다.

이 검증이 있으면 발표에서 "그냥 점수 냈어요"가 아니라 "심어둔 공격 중 몇 %를 탐지한 검증된 시스템입니다"라고 말할 수 있다 → 포트폴리오 가치 급상승.

## 11. 운영 가드레일 (16시간 성패를 가르는 것)

1. **정규화 타임박스 + 체크포인트 배포.** 2:00–5:00을 하드 타임박스로 잡고, 끝에 멘토가 미리 만들어둔 타입별 정규화 파일과 `daily_features.csv`를 배포한다. 정규화에서 막힌 팀도 5:00부터는 무조건 스코어링 단계로 넘어가게 한다.
2. **Feature는 logon부터 완주 후 확장.** logon 3개로 파이프라인 한 바퀴를 먼저 돌리고 file/device, 그다음 http/email을 얹는다.
3. **answers는 검증 단계까지 봉인.** 미리 보면 검증이 무의미해진다.
4. **개념은 인라인 15분.** 별도 강의 블록을 만들지 않는다. 필요한 순간(z-score, 가중치)에 짧게 설명하고 바로 코드로.

## 14. 함정 & 팁
- 가장 큰 함정: 검증 불가 → answers 폴더로 해결 (멘토 필수 준비).
- ML 욕심 금지 → 통계 기반으로 충분, ML은 블랙박스라 설명이 안 됨.
- 점수만 내고 끝내면 약함 → "왜"를 반드시 붙이게.
- 평가일을 baseline에 포함하면 미래 데이터 누수 → `shift(1)` 또는 고정 학습 기간 사용.
- std=0 나눗셈 폭발 → 명시적 rule score와 z-score 상한 적용.
- USB 복사 직접 컬럼이 없음 → device 연결 구간과 file 이벤트를 결합하되 "복사 확정"으로 과장하지 않음.
- 샘플링 주의 → http/email을 날짜 비율로 줄였으니, 인사이더 활동 기간이 샘플에 포함됐는지 확인.
- answers로 가중치를 조정한 결과는 독립적인 최종 성능이 아님 → 튜닝 전·후 결과를 분리.
- 잘 되면 결과물이 "진짜 제품 같아서" 임팩트가 큼.

## 15. 심화 옵션 (여유 있는 팀·잘하는 팀)
- **개인 baseline vs 집단(peer group) baseline.** LDAP 조직도를 붙여 "같은 부서·직무 대비"로도 z를 계산. 개인 이력이 부족한 신입 사용자를 집단 baseline으로 보완.
- **http/email 심화 feature.** 유출·구직 사이트 방문, 첨부가 있는 외부 대용량 메일 등 유출 연관 신호 추가.
- **IQR·백분위 기반 이탈.** z-score가 잘 안 맞는 치우친 분포(bytes 등)에 대안 지표 적용.
- **간단 UI.** Streamlit으로 위험 사용자 조회·드릴다운 화면.
