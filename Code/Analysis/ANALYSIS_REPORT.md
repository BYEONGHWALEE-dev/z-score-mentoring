# CERT r4.2 멀티 로그 z-score 분석 보고서

## 1. 결론부터

축소된 5종 로그를 모두 사용해 1,000명, 2010-01-02~2011-05-17,
464,687 사용자-일자(user-day)를 분석했다.

가장 중요한 결과는 다음과 같다.

- 정답을 보지 않고 만든 **일반 행동 z-score**는 상위 10명 중 9명,
  상위 20명 중 17명, 상위 50명 중 28명의 실제 인사이더를 찾았다.
- 위협 의미 feature까지 추가한 **hybrid score**는 상위 10명 중 8명,
  상위 20명 중 15명, 상위 50명 중 30명, 상위 100명 중 36명을 찾았다.
- 상위권에서는 일반 행동 점수가 더 좋고, 범위를 50~100명으로 넓히면
  hybrid가 조금 더 좋았다. 의미 feature를 추가한다고 항상 성능이 좋아지는
  것은 아니었다.
- 시나리오 1은 매우 잘 잡혔다. 30명 중 27명이 hybrid 상위 50명 안에
  들었고, 중간 순위는 19.5위였다.
- 시나리오 2는 상위 50명 안에서 한 명도 잡히지 않았다. 하지만 사건 기간의
  점수는 30명 모두 각자의 평소 중 상위 10% 안에 들었다. 즉 “개인 변화”는
  감지했지만, 1,000명 전체를 한 줄로 세웠을 때 다른 강한 이상에 밀렸다.
- 시나리오 3은 10명 중 3명이 상위 50명 안에 들었고, 7명은 정답 사건 기간에
  자신의 전체 기간 최고점이 발생했다.
- LDAP에서는 70명 모두 사건 종료 월 또는 그 다음 월에 명부에서 사라진다.
  따라서 이 데이터셋에서는 “퇴사 무렵 위험 행동”이라는 관계가 강하다.
  다만 LDAP는 월별 스냅샷이므로 정확한 퇴사일은 알 수 없으며, 미래의 명부
  소멸을 현재 점수에 넣으면 데이터 누수가 된다.
- 축소 로그에는 정답 `http` 이벤트의 4.74%, `email` 이벤트의 50.64%만
  남아 있다. 반면 `logon`, `device`, `file` 정답 이벤트는 100% 남아 있다.
  웹·메일 시나리오의 탐지 한계를 해석할 때 반드시 이 사실을 밝혀야 한다.

이 결과는 “z-score만 있으면 내부자 70명을 전부 잡는다”는 뜻이 아니다.
z-score는 사용자의 평소 대비 변화를 잘 포착하지만, 장기간에 걸친 점진적
행동, 정상적으로도 USB를 자주 쓰는 사용자, 샘플에서 빠진 희소 이벤트에는
한계가 있다.

## 2. 분석 대상

실제 입력은 `Data/Data for Class/`이다.

- `logon.csv`: 854,856행
- `device.csv`: 405,377행
- `file.csv`: 445,578행
- `http.csv`: 1,422,900행
- `email.csv`: 1,314,400행
- `LDAP/*.csv`: 월별 조직·인사 스냅샷
- `psychometric.csv`: 성격 점수. 이번 점수에는 사용하지 않았다.
- `Data/archive/answers/`: 점수 확정 후 채점에만 사용

`http`와 `email`은 날짜별 결정적 해시 샘플이다. 원본 행을 앞에서부터
자른 것이 아니므로 500일 전체가 보존되어 있지만, 개별 악성 이벤트가
표본에서 빠질 수 있다.

정답 파일은 두 층으로 구성된다.

1. `answers/insiders.csv`는 데이터셋, 시나리오, 사용자, 사건 시작·종료 시각을
   담은 사건 목록이다.
2. `answers/r4.2-*/*.csv`는 해당 사건을 구성하는 실제 로그 이벤트를 시간순으로
   담는다. 행마다 로그 타입이 달라 길이가 다른 파일이므로 일반적인 CSV 표처럼
   한 번에 읽지 않고 `csv.reader`로 처리했다.

## 3. 정답을 봉인한 분석 순서

이번 코드가 따르는 순서는 아래와 같다.

### 3.1 위협 가설을 먼저 정의

answers의 사용자 ID나 사건 기간을 사용하지 않고 다음 도메인 논리를 세웠다.

- USB 연결 중 파일 접근은 유출과 가까우므로 높은 가중치
- 비근무시간 USB·로그인은 위험 신호지만 야근일 수 있으므로 단독 확정 금지
- 외부 첨부 메일과 외부 메일 크기는 외부 반출 가능성을 높임
- 여러 수신자에게 보내는 메일은 계정 오용이나 대량 발송 가능성을 높임
- 구직·유출·키로거 관련 URL은 의미가 강하지만 샘플링과 문자열 룰에 취약함
- 단순 로그량과 서로 다른 PC·파일·도메인 수는 보조 신호

가중치는 이 논리를 코드 상수로 고정했다. answers의 순위 결과를 보고
가중치를 재조정하지 않았다.

### 3.2 5종 로그를 사용자-일자 feature로 집계

`content`는 분석에 사용하지 않고 처음부터 읽지 않았다.

로그온 feature:

- 일별 Logon 횟수
- 비근무시간 Logon 횟수
- 로그인한 서로 다른 PC 수

기기·파일 feature:

- USB Connect 횟수
- 비근무시간 USB Connect 횟수
- USB를 연결한 서로 다른 PC 수
- 파일 접근 수와 서로 다른 파일 수
- 비근무시간 파일 접근 수
- 동일 사용자·PC에서 Connect와 다음 Disconnect 사이에 발생한 파일 접근 수
- USB 연결 구간의 `.exe` 파일 접근 수

웹 feature:

- 웹 이벤트 수와 서로 다른 도메인 수
- 비근무시간 웹 이벤트 수
- 구직 사이트, 유출 사이트, 키로거 관련 URL 수

메일 feature:

- 메일 수
- `@dtaa.com` 밖의 주소가 수신자에 포함된 외부 메일 수
- 첨부가 있는 외부 메일 수
- 외부 메일의 `size` 합계
- 비근무시간 메일 수
- 수신자 20명 이상인 메일 수

USB feature는 “복사 완료”가 아니다. CERT r4.2 `file.csv`에는 복사 목적지를
나타내는 컬럼이 없으므로, 결과를 **USB 연결 중 파일 접근**이라고만 해석한다.

### 3.3 미래를 보지 않는 개인 baseline 생성

각 사용자의 평가일 이전 60일을 baseline으로 사용한다.

```text
baseline_mean(t) = mean(log(1 + x) over previous 60 days)
baseline_std(t)  = std(log(1 + x) over previous 60 days)
z(t) = (log(1 + x(t)) - baseline_mean(t)) / baseline_std(t)
```

- 현재 날짜는 `shift(1)`로 baseline에서 제외했다.
- 최소 14일이 쌓이기 전에는 점수를 0으로 두었다.
- 음의 z-score는 위험 증가가 아니므로 0으로 만들었다.
- z-score는 최대 10으로 잘라 한 feature의 독점을 막았다.
- baseline 표준편차가 0인데 값이 새로 발생하면 z=6 규칙 점수를 부여했다.
- 로그량과 메일 크기의 긴 꼬리를 줄이기 위해 `log1p` 후 z-score를 계산했다.

### 3.4 두 점수를 별도로 생성

`generic_score`는 시간·빈도·규모·외부 통신 같은 일반 행동 feature만 쓴다.
특정 CERT 시나리오를 연상시키는 도메인 문자열은 제외한다.

`hybrid_score`는 generic feature에 아래 의미 feature를 더한다.

- 구직 사이트
- 유출 사이트
- 키로거 사이트
- USB 연결 중 실행 파일

두 점수를 분리한 이유는 특정 문자열 룰의 효과를 일반적인 행동 이상탐지와
혼동하지 않기 위해서다.

### 3.5 정답 없이 상위 후보를 맥락 검토

순위를 먼저 확정하고 아래 파일을 저장한다.

- `results/blind_scoring_manifest.json`: 가중치와 z-score 설정
- `results/blind_user_risk_ranking.csv`: 정답 라벨 없는 전체 순위
- `results/blind_top50_context_review.csv`: peak 시점 이전 최신 LDAP 직무 맥락

LDAP 검토는 “IT 관리자는 무조건 정상”처럼 일괄 감점하기 위한 것이 아니다.
같은 행동도 직무에 따라 해석이 달라지는지 조사하기 위한 것이다.

특히 CERT 시나리오 3의 실제 공격자는 시스템 관리자다. 따라서 관리자라는
이유만으로 새벽 로그인이나 다중 PC 신호를 낮추면 진짜 공격을 놓칠 수 있다.
직무별 보정이 필요하면 임의 감점보다 **같은 직무 동료 대비 baseline**을
추가하는 편이 안전하다.

### 3.6 순위 동결 후 answers로 채점

blind 순위와 설정 파일을 쓴 다음에만 코드가 answers를 읽는다.

- 상위 K 사용자 중 실제 인사이더 수
- Precision@K와 Recall@K
- 시나리오별 중간 순위
- 사용자 자신의 사건 기간 점수가 전체 재직 기간 중 어느 백분위인지
- 사용자의 전체 peak가 정답 사건 기간 안에 들어오는지
- 정답 이벤트 ID가 축소 로그에 실제로 남았는지
- 사건 종료 월과 LDAP 명부 소멸 월의 관계

이 구조는 코드 실행 순서에서도 점수 계산과 사후 채점을 분리한다.

## 4. 실제 탐지 결과

### 4.1 사용자 순위 성능

일반 행동 z-score:

- Top 10: 9명 적중, Precision 90%, Recall 12.86%
- Top 20: 17명 적중, Precision 85%, Recall 24.29%
- Top 50: 28명 적중, Precision 56%, Recall 40.00%
- Top 100: 35명 적중, Precision 35%, Recall 50.00%

Hybrid score:

- Top 10: 8명 적중, Precision 80%, Recall 11.43%
- Top 20: 15명 적중, Precision 75%, Recall 21.43%
- Top 50: 30명 적중, Precision 60%, Recall 42.86%
- Top 100: 36명 적중, Precision 36%, Recall 51.43%

Top 10에서 90%가 정답이라는 결과는 강하다. 다만 인사이더가 70명이므로
Top 10 Recall은 최대 14.29%밖에 될 수 없다. 운영에서는 조사 가능 인원 수를
반영해 Top 20, Top 50, Top 100을 함께 봐야 한다.

Hybrid가 generic보다 항상 좋지 않은 이유도 중요하다.

- 의미 feature가 없는 날에는 분모만 커져 강한 일반 이상점수가 희석될 수 있다.
- 샘플링으로 `http` 95%와 `email` 약 50%가 사라졌다.
- 도메인 문자열 규칙은 정상적인 업무·구직 사이트를 잘못 표시할 수 있다.
- 특정 공격에 강한 feature가 전체 공격 유형에 공통으로 강한 것은 아니다.

따라서 수업에서 “feature를 많이 넣으면 무조건 좋아진다”가 아니라,
추가 전후 결과와 이유를 비교하게 해야 한다.

### 4.2 상위권에서 실제로 수상했던 행동

Hybrid 상위 8명은 모두 실제 인사이더였다.

- 1위 `CAH0936`: USB 연결 중 파일 15건, 비근무시간 USB 7회,
  USB 구간 실행 파일 1건
- 2위 `BDV0168`: USB 연결 중 파일 21건, 비근무시간 USB 8회,
  비근무시간 파일 21건
- 3위 `JRG0207`: USB 연결 중 파일 10건, 비근무시간 USB 7회,
  비근무시간 파일 10건
- 4위 `KLH0596`: USB 연결 중 파일 26건, 비근무시간 로그인,
  비근무시간 USB 9회
- 5위 `BTL0226`: 평소 거의 없던 USB 구간 파일 3건과 비근무 파일 3건이
  각각 z=10
- 6위 `MAR0955`: USB 연결 중 파일 24건, 구직 사이트, 비근무 USB
- 7위 `RKD0604`: USB 연결 중 파일 22건, 비근무 USB 9회,
  비근무 파일 22건
- 8위 `MCF0600`: USB 연결 중 파일 27건, USB 구간 실행 파일,
  비근무 USB 8회

9위 `RSC0089`와 10위 `AHD0848`은 사후 정답상 인사이더가 아니었다.
그러나 answers를 보기 전 단계에서는 “오탐”으로 단정하면 안 된다.
각각 비근무시간 USB·파일·실행 파일, 비근무 USB·웹·외부 첨부 메일이라는
조사할 만한 근거가 있다. 정답 파일은 합성 데이터에서 심은 공격 여부를
말할 뿐, 그 행동이 보안 운영상 조사 가치가 없다는 뜻은 아니다.

### 4.3 시나리오 1: 퇴사 전 야간 로그인·USB·유출 사이트

- 인사이더 30명
- 사건 기간 중간값 약 6.19일
- 정답 이벤트: logon 138, device 138, http 69
- Generic 중간 순위 18.5위, Hybrid 중간 순위 19.5위
- Hybrid Top 10에 8명, Top 50에 27명
- 30명 모두 사건 기간 점수가 자신의 전체 기간 상위 10% 안
- 25명은 상위 1% 안
- 9명은 사건 기간에 전체 최고점 발생

이 시나리오는 비근무시간과 USB라는 강한 generic 신호가 여러 개 동시에
발생한다. 그래서 `http` 악성 이벤트가 5%만 남았어도 잘 잡힌다.

전체 peak가 사건 기간과 정확히 겹친 사용자는 9명뿐이지만, 27명이 사용자
순위 Top 50에 든다. 일부 사용자는 정답 사건 직전에도 비슷한 야간 USB
행동으로 더 높은 점수를 받았기 때문이다. 즉 사용자 식별은 잘하지만
“정답지에 적힌 바로 그날”의 정밀 위치 지정은 더 어렵다.

### 4.4 시나리오 2: 장기간 구직 후 USB 사용 증가

- 인사이더 30명
- 사건 기간 중간값 약 56.19일
- 정답 이벤트: device 2,607, http 3,738, email 420
- Generic 중간 순위 365.5위, Hybrid 중간 순위 255위
- Generic/Hybrid 모두 Top 50 적중 0명
- 30명 모두 사건 기간 점수가 자신의 전체 기간 상위 10% 안
- 29명은 상위 5% 안, 25명은 상위 1% 안
- 10명은 사건 기간에 자신의 전체 최고점 발생

이 결과는 z-score의 중요한 한계를 보여준다.

1. 약 두 달에 걸친 점진적 변화는 하루짜리 폭발적 이상보다 peak 점수가 낮다.
2. rolling baseline이 변화한 행동을 조금씩 새 정상으로 흡수한다.
3. 전체 사용자 peak 순위에서는 시나리오 1의 야간 USB 폭증에 밀린다.
4. 주요 정답 신호인 웹은 4.74%, 메일은 50.64%만 표본에 남는다.
5. 단순 “하루 최대점수”는 지속적으로 중간 강도의 위험이 누적되는 패턴을
   충분히 표현하지 못한다.

즉 시나리오 2를 “전혀 못 잡았다”고만 말하면 틀리다. 개인 내부에서는 사건
기간이 거의 항상 극단값이지만, 현재의 사용자 최종 집계 방식이 이를 Top 50
우선순위로 끌어올리지 못했다.

논리적으로 개선하려면 answers에 맞춰 가중치를 바꾸는 대신 다음을 실험한다.

- 일별 최대값 외에 최근 30일 상위 5일 평균
- 30일 연속 상승 추세(slope)
- 과거 90일 대비 최근 14일 USB 사용률 변화
- 새로 등장한 도메인 비율
- 장기간 job-site 방문의 지속성

이 개선안은 “장기·점진적 위험은 peak 하나로 약하다”는 모델 진단에서
나온 것이며, 특정 정답 사용자 ID에 맞춘 조정이 아니다.

### 4.5 시나리오 3: 관리자의 키로거·상사 PC·대량 메일

- 인사이더 10명
- 사건 기간 중간값 약 1.41일
- 정답 이벤트: logon 60, device 40, file 10, http 53, email 50
- Generic 중간 순위 109.5위, Hybrid 중간 순위 66.5위
- Hybrid Top 50에 3명
- 7명은 사건 기간에 자신의 전체 최고점 발생

Hybrid가 generic보다 중간 순위를 43계단 개선했다. 키로거 URL과 USB 구간
실행 파일이 실제로 도움이 됐다. 다만 웹·메일 샘플에서 핵심 단일 이벤트가
빠질 가능성이 높고, 관리자는 원래 여러 PC와 시스템을 다룰 수 있어 단순
PC 수만으로는 구분이 어렵다.

이 시나리오는 직무 맥락을 이유로 관리자 신호를 일괄 감점하면 안 되는
반례다. 더 적절한 개선은 다음과 같다.

- LDAP의 supervisor를 이용해 “자기 PC가 아닌 상사 PC 로그인” 탐지
- 평소 사용 PC 집합과 당일 PC 집합의 차이
- 사용자 표시 ID와 실제 로그인 주체를 구분할 수 있는 인증 로그가 있다면 활용
- 수신자 20명이라는 고정 기준 대신 개인·직무별 수신자 수 baseline

## 5. 퇴사 직전이 실제로 위험한가

이 데이터에서는 그렇다. 하지만 두 가지 의미를 구분해야 한다.

### 5.1 사후 설명

LDAP 월별 스냅샷을 보면 다음과 같다.

- 70명 전원이 사건 종료 월 또는 다음 월에 처음 명부에서 사라진다.
- 48명은 사건 종료와 같은 월에 명부 소멸 전환이 나타난다.
- 22명은 다음 월에 나타난다.
- 시나리오 1은 같은 월 11명, 다음 월 19명
- 시나리오 2는 같은 월 27명, 다음 월 3명
- 시나리오 3은 10명 모두 같은 월

이는 “퇴사 무렵 위협 행동”이라는 CERT 시나리오 설계와 일치한다.

### 5.2 실시간 탐지 feature

과거 파일을 모두 본 뒤 “다음 달 LDAP에서 사라질 사람”을 현재 점수에 넣으면
미래 정보 누수다. 월별 LDAP에는 정확한 퇴사 시각도 없다. 따라서 현재 분석은
퇴사 proximity를 점수에 사용하지 않고 사후 관계 확인에만 썼다.

실무에서 합법적으로 이용 가능한 정보는 별도다.

- 이미 접수된 퇴사 예정일
- 계정 종료 예약
- 자산 반납 예정
- HR이 승인한 notice period

이 정보가 사건 발생 시점에 이미 알려져 있었다면 위험 맥락으로 사용할 수
있다. 반대로 다음 달 조직도에서 사라진 사실을 과거 탐지에 소급 적용하면
안 된다.

또한 이 데이터의 모든 인사이더가 퇴사하도록 설계됐다는 사실 때문에,
여기서 관찰한 100% 관계를 실제 회사의 일반 법칙으로 해석할 수 없다.

## 6. 축소 데이터가 정답 검증에 미친 영향

정답 상세 파일의 이벤트 ID와 수업용 로그 ID를 직접 대조했다.

- `device`: 2,785 / 2,785, 100%
- `logon`: 198 / 198, 100%
- `file`: 10 / 10, 100%
- `email`: 238 / 470, 50.64%
- `http`: 183 / 3,860, 4.74%

이는 샘플러가 예상 비율대로 동작했다는 증거이기도 하다. 동시에 웹·메일
기반 탐지 성능은 원본 데이터 성능이 아니라 **현재 축소본 성능**이다.

희소하지만 결정적인 단일 이벤트는 표본에서 빠질 수 있다. 수업에서 모든
로그를 다 쓰되 정답 시나리오를 최대한 보존하려면 두 가지 선택이 있다.

1. 현재 표본을 그대로 사용하고, 이 한계를 분석 결과에 명시한다.
2. 일반 행은 현재 비율로 샘플링하되 정답 기간을 모르는 상태에서 보존 가능한
   보안 도메인·희소 이벤트를 별도 층화 표본으로 추가한다.

두 번째 방법에서도 answers의 이벤트 ID를 보고 행을 강제로 넣으면 평가
누수가 된다. 도메인·외부 발송·대량 메일 같은 사전 보안 규칙으로 층화해야 한다.

## 7. 현재 결과를 수업에서 읽는 방법

권장 실습 흐름은 다음과 같다.

1. 학생들은 위협 가설과 가중치 이유를 한 문장씩 기록한다.
2. `generic_score`로 첫 순위를 만든다.
3. answers 없이 상위 후보의 실제 로그와 LDAP 직무를 검토한다.
4. 조정이 필요하면 “어떤 정상 맥락 때문에 어떤 룰을 바꿨는지” 기록한다.
5. 특정 직무 일괄 감점보다 peer baseline이나 새로운 맥락 feature를 우선한다.
6. 가중치와 순위를 파일로 동결한다.
7. 그 뒤 처음으로 answers를 열어 Precision@K, Recall@K, 기간 적중률을 계산한다.
8. 못 잡은 시나리오는 “가중치 숫자”가 아니라 feature·시간 집계·샘플링 중
   무엇이 원인인지 분해한다.
9. answers를 본 뒤 만든 v2는 탐색적 개선으로 표시하고, v1의 최종 검증 성능을
   덮어쓰지 않는다.

이번 결과에서 가장 좋은 토론 질문은 다음과 같다.

- 왜 generic이 Top 10에서 hybrid보다 좋았는가?
- 왜 시나리오 2는 개인 백분위가 높은데 전체 Top 50에는 없는가?
- 관리자 직무를 감점하면 시나리오 3에 어떤 일이 생기는가?
- 웹 5% 표본으로 웹 기반 공격 탐지 성능을 공정하게 평가할 수 있는가?
- 최대 일별 점수 대신 지속성을 반영하면 어떤 정상 사용자도 함께 올라오는가?

## 8. 한계

- 이번 분석자는 CERT 시나리오 설명을 이미 알고 있다. 코드 실행상 answers
  사용자·기간·이벤트는 점수 확정 후에만 읽지만, 완전한 미지 데이터에 대한
  독립 holdout 실험은 아니다.
- 구직·유출·키로거 도메인 목록은 위협 가설이면서 CERT 시나리오 지식의 영향을
  받는다. 그래서 generic과 hybrid 결과를 분리했다.
- 가중치는 도메인 논리로 정한 v1이며 조직별 비용 함수나 조사 인력에 맞춘
  calibration은 하지 않았다.
- 사용자별 첫 14일은 baseline 부족으로 점수가 0이다.
- 월별 LDAP는 정확한 입·퇴사일을 제공하지 않는다.
- `content`를 사용하지 않았으므로 본문 의미 분석은 범위 밖이다.
- 정답에 없는 사용자를 모두 “안전”이라고 볼 수 없다. 합성 데이터에서
  red-team 사건이 아니라는 뜻일 뿐이다.
- 일별 최대점수는 짧고 강한 공격에 유리하고 장기 저강도 공격에 불리하다.

## 10. 최종 판단

현재 축소 데이터만으로도 설명 가능한 z-score 프로젝트는 충분히 성립한다.
특히 강한 단기 야간·USB 행동은 매우 높은 정밀도로 우선순위화했다.

그러나 “퇴사 직전이면 위험”을 점수 규칙으로 넣거나, answers를 보고 70명을
끌어올리도록 가중치를 조정하면 안 된다. 퇴사 관계는 사후 발견이며, 현재
결과에서 개선해야 할 핵심은 장기 지속성, 직무별 peer baseline, 샘플링된
희소 이벤트의 보존이다.

가장 정직한 발표 문장은 다음과 같다.

> 정답을 보지 않고 고정한 일반 행동 z-score가 상위 10명 중 9명의 실제
> 인사이더를 우선순위화했다. 전체 70명 중 절반은 상위 100명에서 찾았고,
> 장기간 점진형 시나리오와 웹·메일 샘플 손실이 주요 미탐 원인이었다.
